## 2. 架构与工程评价

**做得好的地方**

- 分层清晰：`api → service → (dsh / git / execx / ws)` 边界干净，`ws.Source` 接口反向注入避免环形依赖。
- 硬性约束守得住：只调 `dsh --profile headless`、模型走 `--patch` 注入、工作区隔离、`permission_mode=workspace-write`，并有 `workspace_env_test.go` 守回归。
- 幂等与恢复设计到位：`CanResumeFinalize` / `ensureWorkspace` 支持从补丁重建工作区；`scanner` 做崩溃恢复；`CompactDuplicateEvents` 做历史数据收敛。
- 证书/密钥处理基本正确：AES-256-GCM、刷新令牌只存 hash、API Key 只在内存传递并做命令脱敏。

**主要技术债**

1. **多租户是"半套"**：`Project/Repo/Event/Task` 有 `tenant_id` 且用 `h.tdb()` 过滤，但 `Rule`、`TaskLog`、`CredentialUsage`、`Setting` 要么没过滤要么没字段（P0-2、P1-1）。建议统一到 `tdb()`，并补一条"全表扫描 `h.db` 必须显式说明理由"的约定。
2. **权限模型缺服务端二次校验**：权限只做到"接口级"，没有"资源级"；角色权限码无白名单（P0-5）。
3. **高权限配置暴露给 Web**：command_template / release_hook 本质是代码执行入口（P0-6）。要么从 Web 收回，要么加白名单 + 二次确认 + 审计。
4. **进程与并发生命周期**：execx 杀进程组缺失、任务抢占非原子、工作区目录冲突、config 热改竞争 —— 是当前最可能在线上出怪事的四件事。
5. **错误处理风格不统一**：大量忽略错误 + 直接把内部错误回传前端，既不可观测也不安全。

## 3. 修复路线建议

**第一批（本周，止血）**
1. 轮换生产库密码，`server/configs/config.yaml` 去敏，改 `AUTOMEDIC_` 环境变量注入，清理 Git 历史。
2. `Rule` / `TaskLogs` 加租户过滤；`CreateRule` 写 `tenant_id`。
3. `CreateUser` 去掉 `is_super` 入参（仅超管可设）；`SetRolePermissions` 增加权限码白名单校验。
4. 修 ws double close；execx 增加进程组回收。
5. 容器加非 root 用户；CORS 收敛；JWT 无密钥时拒绝启动。

**第二批（两周内，稳）**
6. 任务原子抢占 + 工作区路径带 taskID；Confirm 路径清理指令文件并收窄 `git add`。
7. 登录限流与审计；`ServerError` 脱敏；git 错误回传前剥离 URL 凭据；`SetTrustedProxies`。
8. `UpdateSettings` 改 DB 持久化 + 原子替换，或明确只读。

**第三批（规划）**
9. 收回或加固 command_template / release_hook；补 auth / dsh / ws 单测与越权回归用例；引入版本化迁移替代 AutoMigrate + 手工 SQL 双轨；清理占位死代码。
