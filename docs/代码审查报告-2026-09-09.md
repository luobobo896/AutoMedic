- 审查时间：2026-09-09
- 范围：全仓当前 `main`（含未推送的 `6dd5c71`），对照 2026-09-08 报告复核「已修」项，并覆盖安全 / 任务执行 / 前端 / 部署
- 方法：源码通读 + 四路并行专项（RBAC 租户、任务并发、前端、部署）+ 对关键路径二次核对
- 基线：2026-09-08 报告中多数 P0 已落地；本轮重点是**修复不完整留下的旁路**，以及任务 Confirm 路径把工作区锁重新打开

本报告只列当前仍成立的问题。已关闭项见文末对照表。

## 结论（先看这个）

系统分层清楚，租户过滤在 Project/Repo/Rule/Event/Task 的 REST 读路径上基本到位，容器已非 root，CORS 空配置 403 回归已修。

当前最大风险不是「完全没隔离」，而是：

1. **持有 `settings:update` 或 `project:update` 就能在主机上跑任意 shell**（P0-6 仍开，且 developer 默认可写 `release_hook`）。
2. **租户管理员可把用户绑到平台 `super_admin` 角色**，绕过 `is_super` 入参限制。
3. **WebSocket 任务订阅只验登录、不验租户、不验 `task:read`**，HTTP 日志隔离被旁路。
4. **Confirm 不持仓库锁、不原子抢占**，半自动确认可与同仓执行任务互踩共享工作区。

建议本周只做这四件事，再谈 UI 与部署卫生。

## P0 — 必须先修

### P0-A Web 可改命令模板 / 发布钩子 → 主机 RCE（旧 P0-6，未修）

- 位置：`server/internal/api/handlers.go:121-195`、`server/internal/dsh/runner.go:145-147`、`server/internal/service/task.go:416-429`、`server/internal/api/resource.go:121-124`
- 证据：`UpdateSettings` 可写 `command_template`、`use_shell`、`git.release_hook`；`UseShell=true` 时 `sh -c` 执行模板；`finalize` 用 `/bin/sh -c` 跑 hook，项目 `release_hook` 可覆盖全局。
- 权限面：`tenant_admin` 经 `tenantBusinessPermissions()` 拿到 `settings:update`；`developer` 默认有 `project:update`。
- 影响：租户管理员或开发者可在服务进程用户下执行任意命令。容器已是 `appuser`，但仍是应用主机 RCE（读密钥、改工作区、打内网）。
- 建议：从 API/UI 收回这三项，或仅允许配置文件/环境变量；至少从 `tenant_admin`/`developer` 默认权限里拿掉 `settings:update`，并对 hook 做白名单。禁止 Web 选择 `danger-full-access`。

### P0-B 绑定任意 `role_ids` 可变成平台超管（P0-4 修复不完整）

- 位置：`server/internal/api/rbac.go:209`、`276-278`、`305-313`；`server/internal/auth/auth.go:143-149`
- 证据：`replaceUserRoles` 对 `role_ids` 不做租户校验，直接 `FirstOrCreate`。`loadPrincipal` 只要角色码是 `super_admin` 就把 `IsSuper=true`。
- 影响：有 `user:update` 的租户管理员枚举到平台 `super_admin`（`tenant_id=0`）角色 ID 后，绑到自己即可跨租户。`CreateUser` 对 `is_super` 入参的限制被绕过。
- 建议：只允许绑定 `role.tenant_id ∈ {当前租户}`；非超管禁止绑定 `tenant_id=0` 或 `code=super_admin` 的角色。

### P0-C WebSocket 任务订阅无租户、无 `task:read`

- 位置：`server/internal/api/router.go:201-206`、`server/internal/ws/hub.go:129-169`、`server/internal/api/handlers.go:80-83`
- 证据：`/ws/tasks/:id` 只挂 `Auth.Middleware()`，没有 `RequirePerm(task:read)`。`ServeTask` 在 Upgrade 后按路径 `taskID` 订阅，不查任务归属。`CheckOrigin` 恒 true。
- 影响：任意已登录用户可订阅任意任务终端（代码路径、命令、栈）。HTTP `TaskLogs` 的租户校验被完全旁路。
- 建议：Upgrade 前校验 JWT + `task:read` + `tdb` 任务归属；`CheckOrigin` 与 `allow_origins` 对齐。

### P0-D Confirm 不持 `lockRepo`，与同仓 Execute 互踩共享工作区（P0-3 旁路）

- 位置：`server/internal/service/task.go:172-174`、`437-484`；`server/internal/git/workspace.go:86`
- 证据：工作区路径仍是 `projectKey/repoID-repoName`（无 taskID）。`Execute` 全程 `lockRepo`；`Confirm`/`ensureWorkspace`/`Prepare` 不取该锁。
- 影响：任务 A 待确认时任务 B 开跑 → `reset --hard` 清掉 A 的未提交改动；或 Confirm 提交中被另一任务 reset → 错提交/丢补丁。
- 建议：Confirm 同样 `lockRepo(repoID)`；中长期工作区目录带 `taskID`。

### P0-E Confirm / 重试推送无原子抢占，可双跑 finalize

- 位置：`server/internal/service/task.go:437-447`；`server/internal/api/task.go:139-146`
- 证据：`Confirm` 先 `First` 再无条件 `Updates(status=running)`，没有 `WHERE status IN (...)` + `RowsAffected`。API 用 `go Confirm(...)`，双击即可并行。
- 影响：双 commit/push、重复发布钩子、状态互相覆盖。
- 建议：与 `Execute` 一样用条件更新抢占；进行中拒绝第二次 Confirm。

## 建议顺序（本周）

1. 收回或锁死 `command_template` / `use_shell` / `release_hook`；从默认角色去掉 `settings:update`。
2. `replaceUserRoles` 校验角色租户，禁止绑定平台超管角色。
3. WS 订阅加 `task:read` + 任务归属；Origin 白名单。
4. Confirm 持 `lockRepo` + 条件更新抢占；Cancel 必须落库且禁止后续 finalize。

第二批：登录限流、SSH known_hosts、写操作防重、编辑禁用 key、scanner 先 cancel 再标失败、钉死 dsh/前端 lockfile。
